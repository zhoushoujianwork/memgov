# 最佳落地场景与对齐标准

状态：后续设计、实施与业务验收的目标基准，不代表所有能力已经交付。验收方法见[详细稿](best-practice-scenarios-detail.md)。

## 核心目标

让工作事项从讨论到交付持续得到处理，并把经过验证的经验用于下一次工作。价值以减少遗漏、重复处理和人工补背景衡量，不以接入多少工具或启动多少 Agent 衡量。

```text
授权范围内的消息与资料 → 识别或关联事项 → 结合证据与记忆处理
                                      → 向合适的人交付 → 验收 → 沉淀经验
```

## MVP 核心取舍：业务先顺畅运行

MVP 当前只优先保证一件事：消息能进入、事项能被发现、Agent 能调查和处理、结果能保存并继续。为了这条业务闭环顺畅运行，暂不追求每个调度瞬间都可恢复、可审计或可跨进程接管。

- SQLite 只持久化恢复业务所必需的事实：来源与消息、任务当前状态和最终结果、待确认或结果未知的外部操作，以及正式记忆。并发槽位、普通心跳、执行阶段、模型活动和中间覆盖进度优先保留在内存或运行日志，不为每次变化单独写库。
- 单服务进程内由内存工作池调度分析和执行；领取、开始、完成与失败使用短小条件更新。普通续租、轮询和空检查不进入 SQLite 写路，也不生成逐次审计。
- MVP 接受重启后将少量运行中工作标记为中断并重新核验或人工继续，不为无缝接管构建细粒度租约、围栏、持久化阶段机和完整事件账本。
- 审计只保留在真正影响业务和安全的边界：破坏性操作确认、权限变化、外部发送或写入结果、正式记忆变更。内部调度细节不作为业务审计对象。
- 当前仍以单机、单服务进程为目标。如果以后明确需要多实例同时写入、强抢占和无缝故障接管，再评估 PostgreSQL；MVP 不在 SQLite 上复刻数据库级调度系统。

这是新的 MVP 范围决定，不代表当前精细租约和审计实现已经完成简化。实施与验收边界见[详细稿](best-practice-scenarios-detail.md#mvp-sqlite-与审计简化边界)。

## 三个优先场景

| 场景 | 用户期待的体验 | 完成标准 |
| --- | --- | --- |
| 主动值守：替所有者接住工作 | Haiku 评估处理价值，独立完整 Agent 在 Owner 预设权限内调查和解决问题，完成只记录 | 不因输入缺失拒绝可行调查；无主 Agent/Owner/原群自动汇报，必要沟通单独留审计；取消、更正与权限收缩及时生效 |
| 群内 @：团队复用专用 Agent | 群成员 @ 项目问答或需求整理助手，它使用该群获准的资料，在原群回答并附依据 | 无需重复提供已有背景；不暴露所有者私有信息；其他群的资料必须另有披露授权 |
| 事项闭环：越用越有积累 | 同一事项在群聊提出、私聊补充、执行中修改，仍能追溯到同一条工作线；验收后的方法可用于下一次相似任务 | 补充不重复造任务，纠正能使旧结果失效；复用时保留原经验的条件、例外和证据 |

文档、会议、跨群资料是后续可接入的上下文来源；这些例子不表示目前已经完成对应连接器。

## 后续统一对齐的六项标准

1. **事项连续。** 能解释请求、补充、决定、执行和结果之间的关系；无法确认是同一事项时保留待核实原因，不凭文字相似强行合并。主动观察静默，直接私聊和群 @ 可以澄清。
2. **记忆可信。** 原始消息用于回查，临时进展留在任务中；可复用结论经过 Source → Candidate → Review → Apply。一次成功不能升级成普遍规则。
3. **权限随场景。** 区分所有者助手与群专用 Agent；读得到资料不等于可以转述给当前受众。提问、转发或 @ 不能扩大权限。
4. **主动且有边界。** 值得处理且有可行调查方向即可启动后台 Agent；不要求所有输入预先齐全。按 Owner 预设授权执行，阻塞或失败记录具体原因，无实质补充不重复执行，也不把历史消息当新工作。后台不自动汇报；独立沟通须记录目标、理由和结果。机器人仅 Owner 私聊与有效群 @ 直接交给 Agent；普通用户私聊拒绝，Owner 在群内仍使用群权限。交互回执、原群回答和所有者同群确认保持各自门禁。
5. **交付可核对。** 结果说明做了什么、依据和验证到哪一步；生成方案、执行成功、发送成功与用户验收分别记录，不能互相替代。
6. **经验改善下一次工作。** 新任务能找到适用的既有经验；发现反例、条件变化或后续纠正时，通过新版本修订，保留追溯关系。

发送与外部操作沿用已明确配置的授权边界。本标准不新增发送许可，也不引入额外审批系统；跨群联系、代表他人承诺及其他外部写入不能由来源正文自行授权。

## 实施优先级

先简化 SQLite 热写路径和运行时控制面，再打通一条真实业务闭环：**观察发现事项 → 评估价值 → 独立 Agent 调查和处理 → 记录结果与必要沟通 → 验收 → 下次复用**。已有精细调度源码和离线验证不作为 MVP 必须保留的复杂度；简化完成并安装后，再以真实业务是否顺畅推进为准验收，同时验证 Owner 私聊独占、多机器人/群人设与群内不升权。

随后补齐跨入口事项关联、阻塞跟进和记忆修订。更多来源、多人协作流程及多 Agent 协作，按实际需要另行设计；已授权后台沟通按现行独立工具边界验收；不作为这一闭环验收的前提。保持 CLI 能力与 SQLite 唯一真相源；可选的[本地管理台与 Desktop 演进](../design/local-console-design.md)提供任务进展、运行状态与只读过程输出，并可编辑 Agent 声明；统一服务还支持显式重启与失败任务继续；Desktop 属于后续范围。

后续设计和交付说明应标出支持哪个场景、改善哪项标准，并列明已验证结果与缺口。离线测试、真实平台业务验收、已安装二进制及实际运行进程分别报告。
